# The protocol-proxy wire protocol

This is the contract between a `ProtocolProxyManager` and the proxy processes it launches, as implemented by the
Python connectors in this repository (`protocol_proxy.ipc`) and as a port in another language must implement it.
Byte-exact examples of every construct below are in `tests/test_vectors.json`, generated by `tests/make_vectors.py`
and checked against the implementation by `tests/test_protocol_vectors.py`. Dates mark when a construct was added;
everything is current as of 2026-10-22.

## 1. Launch and handshake

The manager launches a proxy as

```
python -m protocol_proxy.proxy [--gevent] <module>:<ProxyClass> --proxy-id <hex> --proxy-name <str>
    --manager-id <hex> --manager-address <host> --manager-port <int> [--inbound-address <host>]
    [--inbound-port <int>] [--encrypt true|false] [--cipher auto|aes-256-gcm|chacha20-poly1305] [--ipc-tls true|false]
    [--manager-dials true|false]
    [--persistent true|false] [--socket-logging true|false]
    [--compress-threshold <int>] [--log-level <LEVEL>] [--<protocol option> <value> ...]
```

A manager may wrap the command in `ssh -o BatchMode=yes -R <manager port>:127.0.0.1:<manager port> [options] host env
_LAUNCHED_BY_PROXY_MANAGER=1 <python> ...` to run the proxy on another host; nothing else changes.

A port is launched the same way by whatever command it registers for (the manager composes the argument list; every
option is `--name value`, booleans as `true`/`false`). The environment carries `_LAUNCHED_BY_PROXY_MANAGER=1`.

On **stdin** the manager writes, then closes: the proxy's token as 32 hex characters, the manager's token as 32 hex
characters, when `--encrypt true` the 32-byte AEAD key as 64 hex characters, and when `--ipc-tls true` one JSON line
`{"ca": <PEM>, "cert": <PEM>, "key": <PEM>}` of TLS material issued by the manager's own CA (2026-10-22). Nothing
secret is on the command line. A proxy launched with `--encrypt true` or `--ipc-tls true` that finds no key or no
material exits with an error.

Exit code 0 after a clean stop (SIGTERM from the manager, manager gone, or a normal end), 1 otherwise. The manager
terminates the process with SIGTERM when it stops, kills it after 5 s, and relaunches it on the next request after an
exit. The proxy watches its parent PID (every 1 s) and stops when re-parented.

**Manager-initiated registration (2026-10-22).** A proxy launched with `--manager-dials true` does not dial the
manager: it listens on `--inbound-address:--inbound-port` and waits. The manager opens a persistent connection to it
and sends `PING` until the proxy registers over that connection (§7); the proxy adopts the connection only when its
frames authenticate as the manager (sender id and token). Everything afterwards travels on that connection.

## 1a. Manifests (2026-10-24)

How a manager learns what to launch and how to key its processes is data, not code: a proxy ships a `proxy.toml`
manifest and the manager, in any language, reads it. Nothing in a manifest is executable.

```toml
[proxy]
name = "mqtt"                       # the proxy's name: the manager key and the first element of a process key
command = ["{python}", "-m", "protocol_proxy.proxy", "--gevent", "protocol_proxy.protocol.mqtt.mqtt_proxy:MQTTProxy"]
header_version = 2                  # the frame header version the proxy speaks

[identity]
keys = ["host", "port"]             # launch options that select the process; absent: the caller's key, as given
must_match = ["username", "password"]   # remotes that share a process must agree on these

[identity.normalize]                # only these: "lowercase", "strip", { default = <value> }
host = ["strip", "lowercase"]
port = [{ default = 1883 }]

[environment]                       # added to the process environment
MQTT_LOG = "info"

[self_test]                         # optional: a command that exits non-zero if the binary is not what it claims
command = ["{manifest_dir}/bin/mqtt-proxy", "--self-test"]
```

The manager runs `command` with `{python}` replaced by its interpreter (the remote one behind an SSH prefix) and
`{manifest_dir}` by the manifest's directory, then appends the standard options of §1 and the protocol-specific launch
options as `--name value`. The process key is `(name, *normalised identity options)` when `keys` is given, else the
caller's key unchanged; two remotes with the same key share a process, and a remote whose `must_match` options differ
from the first remote's is refused.

**Discovery.** A manager searches directories for `<name>.toml` or `<name>/proxy.toml`, first match wins, in this
order: the directories in `PROTOCOL_PROXY_MANIFESTS` (`os.pathsep`-separated; prepended, not replacing the rest), the
user's `~/.config/protocol-proxy/manifests` (`XDG_CONFIG_HOME`), the environment's `<prefix>/share/protocol-proxy/
manifests` (a Python venv's own, under `sys.prefix`), then the system's `/etc/protocol-proxy/manifests`
(`XDG_CONFIG_DIRS`) and `/usr/local/share` and `/usr/share` `protocol-proxy/manifests` (`XDG_DATA_DIRS`). A proxy that
is not a Python package is installed by placing its manifest, and the binary it names through `{manifest_dir}`, in one
of them; no configuration is needed. Python proxies ship their manifest as package data under a
`protocol_proxy.manifests` entry point (value `package.module:filename`); the Python manager reads those as a fallback
after the directories, and `protocol-proxy-manifests export` copies them into the environment's directory for a manager
that cannot read Python metadata. The Python manager no longer imports `protocol_proxy.protocol.<name>` to find a
proxy; a proxy class in the same environment can still be given directly, which yields an equivalent in-memory manifest.

## 2. Transport

TCP on `AF_INET`. Both ends listen: the manager on `--manager-address:--manager-port`, the proxy on
`--inbound-address:--inbound-port`, or the first free port in 22801..22899.

**Per message (default).** The sender connects, writes one frame and either closes (no response expected) or reads
one `RESPONSE` frame and closes. The receiver reads frames until the sender closes; after a frame whose header has no
keep-alive bit it writes the response, if any, and closes.

**Persistent (2026-10-22).** A peer may keep one connection open and send every frame on it, setting the keep-alive bit
(bit 3) on each header. Responses are matched by `request_id`, so requests interleave; handlers run concurrently. A
receiver that sees the keep-alive bit on an accepted connection from an authenticated sender may send its own
requests back on that connection, which is how a manager reaches a proxy whose address it cannot dial. A frame larger
than the sender's threshold (Python: 256 KiB) may be sent on a connection of its own instead. A lost persistent
connection fails the requests pending on it; the next send redials. Persistent sockets should enable TCP keepalive.
Receivers must serve frames until EOF on any connection; a sender may use either policy toward any receiver.

## 3. Frame

A frame is a 2-byte big-endian version word, a fixed header of that version, then `data_length` payload bytes.

| Field | Format | Bytes | Notes |
|---|---|---|---|
| version | `H` | 2 | 1 or 2; 2 is sent by default, 1 is still accepted |
| data_length | `Q` | 8 | payload bytes that follow the header, as they are on the wire |
| method_name | `32s` | 32 | UTF-8, NUL-padded; at most 32 bytes |
| request_id | `I` (`H` in version 1) | 4 (2) | drawn by the sender per header version, cycling from 1; a response carries the request's id |
| sender_id | `16s` | 16 | the sender's proxy id (UUID bytes) |
| sender_token | `16s` | 16 | the sender's token (UUID bytes) |
| bitflags | `H` | 2 | see below |
| remote_id | `16s` | 16 | version 2 only; all zeros when absent |

Version 1 is 76 bytes after the version word, version 2 is 94 (field order in version 2: data_length, method_name,
request_id, sender_id, sender_token, bitflags, remote_id). `struct` notation: version 1 `>HQ32sH16s16sH`, version 2
`>HQ32sI16s16sH16s`.

**bitflags**

| Bit | Name | Meaning |
|---|---|---|
| 0 | response expected | the sender waits for a `RESPONSE` with this `request_id` |
| 1 | compressed | the payload is zlib-compressed (§4) |
| 2 | encrypted | the payload is nonce + AEAD ciphertext + tag (§5) |
| 3 | keep-alive | the sender keeps this connection open for frames in both directions (§2) |
| 4 | AES-GCM | with bit 2: the AEAD is AES-256-GCM instead of ChaCha20-Poly1305 (§5) |

Payloads are UTF-8 JSON before compression or encryption. An empty payload is allowed.

## 4. Compression (2026-10-22)

A sender may zlib-compress a payload (zlib framing, default level) and set bit 1; `data_length` counts the
compressed bytes. It does so only toward a peer that advertised `compress` (§7) and only for payloads above its own
threshold (Python: 4096 bytes). Receivers always accept both forms. Order with encryption: compress, then encrypt;
decrypt, then decompress.

## 5. Encryption (2026-10-22)

When the two ends share a key (§1), every frame between them is encrypted, registration included. The payload on the
wire is a 12-byte random nonce, the AEAD ciphertext of the (possibly compressed) payload, and the 16-byte tag;
`data_length` counts all of it; bit 2 is set. The AEAD is ChaCha20-Poly1305, which every implementation must
accept, or AES-256-GCM when bit 4 is also set (2026-10-23); both use the same 32-byte key, 12-byte nonce and
16-byte tag. A sender uses AES-256-GCM toward a peer only if that peer advertised `aead-aes256gcm` (§7) or the
manager launched it with `--cipher aes-256-gcm`; a receiver decides by the bit, frame by frame. `REGISTER_PEER`
carries the proxy's own choice as `"cipher"`. The associated data is the whole header as sent, version word
through `remote_id`, so method name, request id, sender, remote and flags cannot be altered or replayed onto another
message without detection. The mode is fixed per peer: a receiver refuses a clear-text frame from a peer it shares a
key with and an encrypted frame from one it does not; the refused request fails (or the connection is dropped) and
nothing else is affected. Keys live for the proxy's lifetime; a relaunch gets a fresh one. Peers advertise
`aead-chacha20poly1305`.

**TLS (2026-10-22).** With TLS material both ends speak TLS 1.3 on every connection between them, each requiring the
other's certificate to chain to the manager's CA; the proxy's certificate names the proxy's id and the manager's names
the manager's id, and a frame is accepted only if its sender id matches the certificate it arrived under. A manager's
listener accepts both plain and TLS connections (a TLS record begins with byte 0x16, a frame with 0x00); a proxy with
TLS material accepts TLS only. TLS and the per-message AEAD (§5) are independent and may be combined.

## 6. Authentication and dispatch

A receiver accepts a frame only if `sender_id` names a peer it knows and `sender_token` equals that peer's token;
otherwise the frame is logged and dropped (a request gets an empty reply). Handlers are keyed by `(method_name,
remote_id)` first and `method_name` second; a proxy serving several remotes tags its pushes with the remote's id.

A request that expects a response but names an unknown method, or a method whose handler gives no response, is
answered at once with the error reply of §8 (2026-10-22), so the caller does not wait out its timeout.

## 7. Registration

After its listener exists, the proxy sends `REGISTER_PEER` (response expected) with

```json
{"address": "127.0.0.1", "port": 22802, "proxy_id": "<hex>", "token": "<hex>",
 "features": ["ping", "log", "set_log_level", "compress", "aead-chacha20poly1305", "aead-aes256gcm"],
 "cipher": "aes-256-gcm"}
```

and the manager replies `{"registered": true, "features": ["compress", "aead-chacha20poly1305", "aead-aes256gcm"]}` (older managers
reply plain `true` or `false`; proxies accept both). Two attempts, 5 s response timeout, 20 s between attempts;
failure stops the proxy. Nothing else may be sent before registration succeeds, and the manager sends nothing to the
proxy before it has registered. Each side records the other's `features` and uses only what was advertised.

## 8. Core methods

| Method | Direction | Response | Payload |
|---|---|---|---|
| `REGISTER_PEER` | proxy to manager | yes | §7 |
| `RESPONSE` | either | no | the reply to the request with the same `request_id` |
| `PING` | manager to proxy | yes | empty; reply `{"uptime": <s>, "remotes": <int>, "busy": <bool>, "last_activity": <iso8601 or null>}` |
| `LOG` | proxy to manager | no | `{"records": [<record>...], "dropped": <int>}` (§9) |
| `SET_LOG_LEVEL` | manager to proxy | yes | `{"level": "DEBUG"}`; reply `{"level": "<level in force>"}` |

Protocol vocabularies (`REGISTER_REMOTE`, `READ_POINTS`, `WRITE_POINTS`, `RECEIVE_UNSOLICITED`, ...) are defined by
each driver interface and its proxy. Replies follow `{"result": ..., "error": ...}`; a handler that raised, timed out,
or could not be found answers `{"status": "error", "error": "<text>", "method": "<name>"}`.

## 9. Logging

Before registration, and again for whatever is still queued at exit, a proxy writes its log records to **stderr**, one
JSON object per line with the Python `LogRecord` attribute names (`name`, `levelno`, `levelname`, `pathname`,
`lineno`, `funcName`, `created`, `msecs`, `process`, `msg` already interpolated, `exc_text` for a traceback; other
attributes may be present and are ignored by readers that do not know them). After registration it sends the same
objects in `LOG` batches over the socket, every 0.2 s or 64 records, from a bounded, rate-limited queue; records it
had to drop are counted in `dropped`. On a persistent connection a sender should write LOG frames only when no other
frame is waiting. The manager handles both channels identically and logs the dropped count.

A non-JSON line on stderr is logged at WARNING, on stdout at INFO, unless it starts with a syslog-style severity
prefix: `<7>` DEBUG, `<6>` and `<5>` INFO, `<4>` WARNING, `<3>` ERROR, `<2>`, `<1>`, `<0>` CRITICAL.

## 10. Liveness

The manager sends `PING` to every registered peer it launched every 10 s and expects a reply within 5 s. Any reply
(even an older proxy's unknown-method error) counts; three consecutive misses lose the peer: it is terminated,
forgotten, its users are told, and it is relaunched on the next request. The parent-PID watch in the proxy and TCP
keepalive on persistent connections are the cheaper first signals.

## 11. Compatibility

- Receivers accept header versions 1 and 2; senders should send 2.
- A peer that ignores bits 1 to 3 interoperates as long as it never has them set toward it: nothing is compressed or
  encrypted toward a peer that did not advertise the feature (or was not given a key), and a per-message sender never
  sets keep-alive. A receiver must still serve frames until EOF.
- `PING`, `LOG` and `SET_LOG_LEVEL` are optional for a port; the manager treats an unknown-method error to `PING` as
  life, and a port that never sends `LOG` is simply read from its pipes.
- A port that implements only ChaCha20-Poly1305 omits `aead-aes256gcm` from its features and is never sent AES-GCM.
